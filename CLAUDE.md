# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Huntlog is a Manifest V3 Chrome extension for tracking job applications, built with WXT + React 18 + TypeScript (strict) + Tailwind v4. `spec.md` is the source of truth: read it before building any feature, and update it when a product decision changes. Build order is in `milestones.md` (thin end-to-end slices M0–M9); work one milestone at a time.

## Commands

- `npm run dev`: WXT dev mode. It launches Chrome (via the `web-ext` dev dependency) with the unpacked extension and hot reload. Dev builds add their own permissions; only the production manifest counts for spec §8.
- `npm run build`: production build to `.output/chrome-mv3/`.
- `npm run zip`: Chrome Web Store upload zip in `.output/`.
- `npx vitest run`: all unit and component tests (`lib/`, `components/`, `tests/`).
- `npx vitest run lib/stats.test.ts -t "week start"`: a single test file or test name.
- `npx playwright test`: end-to-end tests in `e2e/`, loading the built extension into a persistent Chromium context. Run `npm run build` first. `e2e/manifest.spec.ts` asserts the built manifest's permissions, so update it when a milestone adds one.
- `npm run screenshots`: every screen at 320px in light and dark into `docs/design-review/screenshots/` (`review/`, a separate Playwright config, not in CI; build first). `node review/copy-deck.ts` regenerates `docs/design-review/copy-deck.md`, every user-facing string by screen.
- `node scripts/render-icons.ts`: renders `assets/icon.svg` (the Huntlog crosshair-and-check icon; `icon-16.svg` is its simpler 16px drawing) to `public/icon/{16,32,48,128}.png` through Playwright's Chromium, the 128px one with the store's 16px of transparent padding. Edit the SVGs, never the PNGs.
- `npm run lint` / `npx tsc --noEmit` / `npx prettier --check .`: ESLint, type check and formatting. ESLint bans `fetch`, `XMLHttpRequest`, `WebSocket` and `EventSource` as bare globals and on `window`/`self`/`globalThis`, plus `navigator.sendBeacon`. It's a guardrail, not a proof: the PR review still checks for network creep.

Gotchas:
- Every file in `entrypoints/` is treated as an entrypoint, so tests for entrypoints go in `tests/`, not next to the file.
- Use WXT's `browser` global (typed), not `chrome`. In Playwright `serviceWorker.evaluate` callbacks the global is `chrome`; declare it as `typeof browser`.
- Playwright can't click native context menus or the toolbar, and its key presses never reach extension shortcuts. `clickToolbarIcon` in `e2e/fixtures.ts` clicks the toolbar icon through CDP (`Extensions.triggerAction`, enabled by `--enable-unsafe-extension-debugging`). That click grants `activeTab` only when `openPanelOnActionClick` is off.
- TypeScript is pinned to `~6.0` because typescript-eslint doesn't support TS 7 yet.

## Architecture (from spec.md §3–§9)

**UI:** the M6 redesign is done (v0.6.0), and the post-M6 design review's decisions (`docs/design-review/README.md`, list in `milestones.md`) have all landed (v0.6.1, PRs #47–#55), so `spec.md` and the sections below agree.

**Local-first, no network.** All data lives in the browser. Applications and Resumes (file Blobs) are in IndexedDB via Dexie (`lib/db.ts`). Settings are in `chrome.storage.local`. Never add fetch calls, analytics, remote code, or host permissions: the Web Store privacy pitch depends on this.

**Permissions are fixed and minimal:** `sidePanel`, `storage`, `unlimitedStorage`, `contextMenus`, `activeTab`, `scripting`. Adding a permission is a product decision that needs a spec change.

**Capture flow spans three pieces:**
1. `entrypoints/background.ts` handles the context-menu click or the keyboard command. That user gesture grants `activeTab`.
2. The background script (`handleCapture`) first calls `chrome.sidePanel.open({ windowId })` synchronously inside the gesture handler, before any `await`, or Chrome rejects it. Then it runs `lib/extract.ts` in the tab via `chrome.scripting.executeScript({ func })` and writes the result through `lib/captureDraft.ts` to `chrome.storage.session` under `captureDraft:<windowId>`. On a restricted page it falls back to the tab URL only. If two captures in one window overlap, only the newest one writes its draft.
3. The side panel (`components/useCaptureDraft.ts`) reads and clears its own window's draft, both on load and on `storage.session` change (the panel can open before the draft exists), and ignores drafts older than 5 minutes. A capture switches `App` to the Add view and remounts the form keyed by capture, so each capture replaces the form's contents and shows the "Auto-filled, please check" hints. The form sets Source from the job's address (`sourceFromUrl`, `lib/captureSource.ts`: well-known job boards on their own domains only) and starts with the remembered resume; `App` latches the Add form with the defaults it mounted with (`addForm`, keyed per sheet), so a change to the defaults while it's open (another window, or this one's Save) never unmounts it; a manual Add mounts once the defaults are ready, a capture waits for them at most `CAPTURE_DEFAULTS_WAIT_MS` from its arrival. Saving or cancelling marks the capture consumed, so it never prefills a later manual Add.

Link context-menu clicks skip extraction and only pass `linkUrl`. Buttons inside the side panel do **not** grant `activeTab`, so the panel can't read the current tab itself.

**`lib/extract.ts` must be fully self-contained.** `executeScript` serializes the function, so it cannot reference imports or outer-scope variables. It must never throw, and it returns partial data (sources tried in order: JSON-LD `JobPosting` → microdata → OG/meta → heuristics, including ATS hostname patterns). Generic extraction only: no per-site scrapers in v1.

**Data invariants (spec §5):**
- UUID IDs, ISO timestamps, and soft deletes (`deletedAt`). Undoing a delete clears `deletedAt` and moves `updatedAt` forward, because future sync is last-write-wins on `updatedAt`. Functions that write inside a Dexie transaction return `undefined` for a missing row and throw `NotFoundError` outside it, since Dexie wraps errors thrown inside. Every query must filter out soft-deleted rows. Reads and writes go through `lib/applications.ts`, not straight to `db` from components, so the filter lives in one place. `deletedAt` isn't indexed (Dexie skips `undefined`), so filter it with `.filter()`. These fields exist to make future cloud sync possible, so keep them on new tables.
- Status rules live in `lib/status.ts` (pure): `applyStatusChange` appends one history entry and applies the Date applied rule (`appliedAtAction`: Applied sets today, statuses that imply an application ask, Saved/Withdrawn don't, a stored date is never overwritten). `setStatus`/`undoStatusChange` in `lib/applications.ts` write it; Undo restores the earlier record only if the row hasn't changed since.
- `statusHistory` is append-only (dates are editable through `updateHistoryDate`, which identifies the entry by index and timestamp so a changed entry isn't edited by mistake, keeps its local time of day, and moves Date applied along with the first Applied entry when they matched). The one exception: Undo of a status change removes the entry that change added. Stats use the *first* entry into a status, so never rewrite history when the status changes.
- The status list is a fixed union of 9 values. Do not make it configurable.
- `urlNormalized` (`lib/normalizeUrl.ts`) and `companyTitleKey` (`lib/dedupe.ts`) drive duplicate detection. Both are derived fields, recomputed by Dexie `creating`/`updating` hooks in `lib/db.ts` on every write that touches `url`, `company` or `title`, so no write path can leave them stale. `findDuplicates()` lives in `lib/applications.ts` with the other reads and takes validated values, not raw input. `normalizeUrl` strips tracking params but keeps job-ID params such as `currentJobId`, `jk`, `gh_jid`. **Changing `normalizeUrl` or `companyTitleKey` rules needs a Dexie migration that recomputes stored values**, or old and new rows stop matching.
- Migrations are tested twice: `lib/db.test.ts` opens a database created with the previous schema (fake-indexeddb), and `e2e/migration.spec.ts` seeds the previous layout from the service worker in real Chrome. Dexie version N is IndexedDB version N × 10.
- A resume an application uses (`isResumeInUse` in `lib/applications.ts`: a live one, or one deleted within its Undo window) is archived, never deleted. Otherwise delete is a soft delete whose file is purged after the Undo window (`purgeDeletedResumeData`). Resume reads go through `lib/resumes.ts`, which owns the resume soft-delete filter. Files live in their own `resumeFiles` table (never load them to list resumes) as `ArrayBuffer`, never `Blob` (fake-indexeddb loses Blobs); `getResumeBlob()` builds one to open. Uploads are checked by extension plus the file's first bytes, not the reported type. `openResume()` (`lib/openResume.ts`) opens a PDF in a new tab at `resume-viewer.html?id=…` (the `entrypoints/resume-viewer/` page reads the file and shows it in an iframe; it owns the blob URL, so it outlives the panel) and downloads other formats. `App` runs `purgeDeletedResumeData()` at startup with a 24 h window (another window's Undo toast can be paused far past a minute); a resume's delete toast purges its file in `onClose` unless Undo was taken. `ResumeUpload` (its drop zone is `FileDropZone`) is the one upload UI (the Resumes tab's upload sheet, and the form's inline group, where Enter in a text field uploads rather than submitting the application, and Enter on the file field is left to the picker). Its file input is visually hidden (`peer sr-only`) and named by aria-labelledby; the drop zone is its `<label data-dropzone>`, so a click anywhere opens the picker and the zone draws the input's focus ring. A drop of exactly one file picks it. `guardFileDrops()` (`components/dropGuard.ts`, installed by `App`) refuses files dragged anywhere outside a `[data-dropzone]`, and links anywhere but a text field, so Chrome never opens a dropped file or link in place of the panel; drags of plain text are left alone. `carriesFiles()` there is the one file-drag test. A drop or pick mid-upload is ignored, and the upload sheet can't close mid-upload. Field errors in small forms (the uploader, rename) use `useFieldErrors` (`components/useFieldErrors.tsx`: linked errors, the first invalid field focused once its error renders). A row or empty state that unmounts while it has focus hands it to the tab's heading (`useFocusRescue`), as does a sheet whose opener has gone by the time it closes. **Resumes tab** (`components/ResumesPanel.tsx`): a search over display and file names (`searchResumes`, every word, accent-insensitive), rows that open or download on tap (`Open <name>`/`Download <name>`, details as the description: format and size, then the upload date on its own line) with a bare vertical `MoreMenu` (`vertical`) (Rename in a sheet, Archive/Unarchive, Delete), an Archived accordion (`useCollapsing`, the same height animation as More details), and the floating **+ Upload** (`App` renders it and owns `uploadOpen`). In tests, use `uploadResume`/`resumeAction` from `e2e/fixtures.ts`. `opensInViewer()` is the single PDF-opens/else-downloads rule; to open a PDF, only check the file exists (`resumeFileExists`), never load it in the panel. In e2e, finish a `download` (e.g. `download.path()`) or closing the browser hangs. Applications also store `resumeNameSnapshot`.

**Settings** (`lib/settings.ts`) live in `chrome.storage.local`, one key per setting (`settings.weeklyGoal`, `settings.weekStartsOn`, `settings.theme`). A write sets or removes only its own keys and never reads first, so windows changing different settings at once can't undo each other, and a failed read can't become a write of defaults. Malformed stored values are dropped, so an absent setting means its default (no weekly goal; week start follows the locale). Writes go through `updateSettings` (a field given as `undefined` clears it; an invalid value throws, so validate first) or `resetSettings`. Components read them with `useSettings()` (`components/useSettings.ts`): one shared copy per page (one read, one `storage.onChanged` listener), so a change in any window applies everywhere and every component sees the same settings.

**Scrollbars** are hidden everywhere (`scrollbar-width: none` plus `::-webkit-scrollbar` for Chrome < 121, in `style.css` base); where hidden content would go unnoticed, fade the edge that has more beyond it with `useEdgeFade(ref, axis, size, trigger)` (`components/useEdgeFade.ts`: Stats' range chips, Notes past twelve lines; sets `data-fade-start`/`data-fade-end` and a mask). Pass a controlled field's `value` as `trigger`; never update state from the field's own input events, since that re-renders it with its old value before React's onChange and the typed text is lost.

**Theme and styles (spec §9):** colors come only from the tokens in `assets/theme.css` (hex, a light set on `:root` and a dark set on `[data-theme='dark']`), used as Tailwind colors (`bg-background`, `text-muted-foreground`, `border-input`, `bg-status-progress`, …). Never write a raw palette class like `text-slate-600` or `bg-indigo-600`: it won't change with the theme. `--success` is the goal card's restrained green. `tests/contrast.test.ts` checks the listed token pairs (text 4.5:1; inputs, focus rings, chart bars and status segments 3:1) in both themes, so add a pair there when you add a token that shows text or a mark. Shared styles live in `entrypoints/sidepanel/style.css` as Tailwind utilities: `btn` plus a variant (`btn-primary`, `btn-outline`, `btn-ghost`, `btn-secondary`, `btn-destructive` (shadcn's tint: `--destructive-solid` at 20% behind `--destructive-solid` text, the owner's choice although under 4.5:1, so it has no contrast pair (`--destructive-foreground` is gone); `--destructive` is for destructive text elsewhere), `btn-link`) and optionally `btn-sm`/`btn-icon`, `field` for inputs/selects/textareas, `field-label`, `field-error`, `card`, `section-heading`, `link`, `focus-ring`. `lib/theme.ts` sets `data-theme` (the resolved theme) and `data-theme-setting` on `<html>` and keeps a `localStorage` mirror; `entrypoints/theme-init.ts` (an unlisted script loaded as a classic `<script src="/theme-init.js" vite-ignore>` in each page's `<head>`) applies the mirror before the first paint. The side panel follows the setting with `useTheme()` in `App`; other pages call `followThemeSetting()`. Every extension page (the panel, `resume-viewer`, `notices`, `privacy`) includes that head script and imports the tokens. Icons are Lucide paths copied into `components/icons.tsx` (decorative, `aria-hidden`); add one from the `lucide-static` package rather than installing an icon library. Geist is bundled as a Latin subset (`assets/fonts/`); its OFL and Lucide's ISC license are on the `notices` page.

**Settings** (`components/SettingsPanel.tsx`): the content of a near-full-height `Sheet` (not dismissible: the goal is a text field) that the header's gear ("Settings", `aria-haspopup="dialog"`) opens over whatever tab is showing, once settings have loaded; `App` owns `settingsOpen`, and `selectTab` clears it (only a capture or a toast's action switches tabs). `settingsShown` lasts until it has slid out, and with a form sheet makes `pageInert`, which holds back focus meant for the page (the restored row after Undo, + Add) until then; a toast closed inside any open sheet leaves focus in that sheet. It's not a tab. Cards for Weekly goal, Display, Your data and About. Its confirmations are sheets on top of it; in e2e, wait for one to close before pressing Escape again, since a sheet sliding out swallows the key. Changes save as they're made (the goal when its field is left or on Enter, never per keystroke, so "201" can't store "20" on the way) and show up in every window through `useSettings`. **Delete all data** (`lib/deleteAll.ts`) is the one permanent delete: it clears `applications`, `resumes` and `resumeFiles` in one transaction (all or nothing), then removes the remembered form defaults and pending capture drafts; settings stay. **Reset settings** resets them, and with "Also delete all my data" ticked deletes first, so a failed delete leaves the settings too. Both need `DELETE` typed (case-sensitive, spaces around ignored), unticking forgets what was typed, and both confirm in a `Sheet`. The sheet tells `App` (`handleDataDeleted`, back to an empty list) as soon as the tables are cleared, even if a later step fails (`LeftoversError`, or the settings reset), and says plainly whether the data is gone. Every window follows the remembered form defaults through `onFormDefaultsChanged`, so none keeps deleted ones. About links to bundled pages (`privacy.html`, a placeholder until M9, and `notices.html`). **Export backup** (`lib/backup.ts`, spec §6) downloads `huntlog-backup-YYYY-MM-DD.json` through `downloadBlob` (`lib/download.ts`, a clicked `<a download>`, no `downloads` permission; `openResume` uses it too): live rows only (plus a deleted resume a live application still links to), only the settings that are set, applications without their derived fields, files base64, written as one Blob part per resume so a large library is never one string. The export's time is `backup.lastExportedAt` in `chrome.storage.local`, shown as "Last backup: …" (`lastBackupText`, local calendar days) and followed across windows by `useLastBackup`. **Import** opens `ImportSheet` (a sheet over Settings, dismissible, not closable mid-import): `parseBackup` (`lib/backupImport.ts`) checks the whole file before anything is written (strict ISO timestamps, `safeHref` URLs, known enums, text limits, resume files through `checkContents` and a `mimeType` from `formatMimeType`; derived fields recomputed, unknown fields dropped, null means absent) and lists every problem. `mergeBackup` (newer `updatedAt` wins, a tie keeps the stored row, settings untouched) and `replaceWithBackup` (clear and `bulkAdd` in one transaction, then the settings and form defaults; a failure after the data is `SettingsRestoreError`) each write in one transaction. Replace asks in a nested "Replace all data?" sheet with `countLiveData`'s counts; its destructive button isn't the shortcut's. `App.handleDataImported` goes back to the list and bumps `listShown` so its frozen order refreshes. `FileDropZone` is the one drop zone (the uploader's and the import's). Busy exports and imports, and "Checking the file…", show `Spinner` (`components/Spinner.tsx`, a CSS-transform spin that Chrome runs off the main thread, so it turns while a big file is parsed; still under reduced motion). **Export CSV** (`lib/applicationsCsv.ts`: `CSV_COLUMNS` is the one column list for the export, the template and the import) writes `huntlog-applications-YYYY-MM-DD.csv` through `lib/csv.ts` (hand-written RFC 4180: `toCsv`, `parseCsv`, a BOM; `neutralizeFormula` prefixes `'` to cells starting with `= + - @`, tab or CR, and `restoreFormulaText` undoes it on import); it doesn't count as a backup. A CSV picked in the Import sheet (by `.csv`, or content not starting with `{`) goes through `planCsvImport` (`lib/csvImport.ts`, pure: columns matched by name in any order, Company and URL required, rows checked by `validateApplication`, statuses, work modes and periods matched loosely, an unknown status → Applied with a warning, a job past Saved without a date kept undated, one history entry, resumes linked by name, `duplicate` against stored rows and earlier rows) into a preview (`CsvPreview`), and `importCsvRows` adds the rows in one transaction, re-checking duplicates and resume links there, and leaving duplicates out unless "Import them anyway". `parseCsv` takes the separator `detectDelimiter` finds (`;` from European Excel) and keeps blank lines so row numbers match a spreadsheet's; `readCsvDate` reads the locale's numeric dates.

**`lib/stats.ts` is pure.** It takes applications, a range and `weekStartsOn`, and returns numbers, which keeps it unit-testable. `resolveRange()` turns a range choice into dates, given `now` (Custom accepts dates from 1970 to today only). `computeStats()` counts Interviews and Offers by *stage*, which is the first entry into Interviewing/Offer/Accepted (or Offer/Accepted), so they agree with the interview rate. `components/StatsPanel.tsx` only picks the range and displays the result (the range is a scrolling radio group of chips, one Tab stop; each time the tab is shown, or the range changes, the chosen chip is scrolled back into view sideways only, by setting the row's `scrollLeft`, since `scrollIntoView` would scroll the tab too; with arrow keys moving focus but not the range, as in a toggle group, `rovingIndex` again; it bleeds to the tab's edges through `--tab-gutter`, which `TabPanel` sets as its side padding; Custom's From/To are in a "Custom range" sheet that applies only on Apply, its errors through `useFieldErrors`, whose `clear(field)` clears just the field being edited; in tests pick with `within(getByRole('radiogroup', { name: 'Range' })).getByRole('radio', { name })`). `DateRangeFields` is the one From/To pair, shared with the list's date filter, so their bounds match. `StatsPanel` gets the week start from `effectiveWeekStart()`: the Settings choice, else `localeWeekStart()` (`lib/locale.ts`). `weeklyGoalProgress()` counts this calendar week's Applied (by Date applied, live rows only) against the goal, whatever range is picked. With a goal set, the first card under the range is `WeeklyGoalCard` (`StatsCharts.tsx`: a region named "Weekly application goal", described by `goalSummary`; this week's count large, "submitted this week"; a five-segment `role="progressbar"` filled per `segmentFill`, `bg-chart-1` below the goal and `bg-success` from it, with a check and "You've reached your goal!"; nothing for a goal that isn't positive), and the range's Applied joins Interviews and Offers in a three-card row; without one, `AppliedCard` shows Applied large, laid out like the goal card, with a pointer to the setting, and Interviews and Offers follow as two cards, then the rates. Rejections appear only inside the neutral outcomes breakdown ("Closed – not selected"), never as a headline stat or in red. Each chart is a `card` with a title and summary; the activity bars are HTML (`data-bar`, rounded tops, dashed gridlines), not a stretched SVG, and size within their slot by width, since percentage padding would be measured against the whole chart.

**Tabs:** `App` holds the selected tab (`TabBar`: Applications, Stats and Resumes, an ARIA tablist with roving focus, each icon beside its label in one row, spanning the panel's full width (at 320px "Applications" has about 5px to spare), and an underline that slides to the selected tab). The panel is a fixed-height column: a header (the title with the Settings gear on its right, then the tab bar), then a clipped viewport (`overflow: clip`, not `hidden`, so focusing into a sliding section can't scroll it sideways) holding every section as a `TabPanel` (`components/TabPanels.tsx`). Every section stays mounted, so tabs keep their state, and each **scrolls on its own** (so it keeps its scroll position; in e2e use `activePanel`/`scrollPanel` from `e2e/fixtures.ts`). `useTabSlide` reports the section sliding out and the direction (`forward` toward later tabs): the new section slides in as the old slides out for `TAB_SLIDE_MS`, the one source for the slide's duration (nothing slides under reduced motion, and a switch made mid-slide is instant). Only the selected section is usable; one sliding out is painted but `inert` and `aria-hidden`, and the rest are `visibility: hidden` plus `content-visibility: hidden` (not `display: none`, which would lose their scroll position). While a form is open, only Applications shows, whatever the tab. Anything `position: fixed` (the floating + Add) renders outside the sections, since a sliding (transformed) section would carry it along. An element that fills the clipped viewport uses `focus-ring-inset`, since an outline outside it would be cut off. ids come from `tabId`/`panelId`. Only a capture (and the deferred-capture toast's Open) switches tabs, and that closes any sheet the tab left behind had open, since a hidden modal sheet would still block the panel: whoever owns a sheet's open state clears it when its tab is left (`App.selectTab` for the upload and Settings sheets; Settings' confirmations, Rename and Stats' Custom range reset theirs during render from an `active` prop), and a Settings delete still running then reports its outcome in a toast; Undo in a toast switches back to Applications to show what it restored. `navigate()` itself never switches tabs.

**Side-panel views:** `App` switches between views with plain component state (no router). The Applications section shows the `base` view (the list or a detail view); Add and Edit open as a sheet over it (`sheetView`, kept until the sheet has finished sliding out, so focus targets reach the list, and Detail's `active` focus logic runs, only once it has gone; the section is `inert` from the moment a form is chosen, even while Edit loads). An Add view carries the capture's `nonce` (0 for a manual Add), so its form keeps one key for its whole life. When a form sheet has gone the list counts as shown again (`shown`), and a just-saved row (`expectRow`) refreshes the freeze once more when it reaches the live query. The floating + Add stays mounted under an Add sheet, so it's the opener focus returns to. With the page inert behind a sheet, focus that needs a new home goes into the sheet (`focusOpenSheet`), not the page. Views: the list (with a floating **+ Add** button, `components/Fab.tsx`, accessible name "Add application", shown only on the Applications list; an empty list also has "Add your first application"), Add, detail and Edit. Closing a view returns focus where the user came from (spec §10): the row they opened, Edit after editing, the restored row after Undo, or the floating + Add when the row is gone. Focus targets live in one `App` state that's cleared once used, so a remounted list never replays an old one. **Async results navigate only if their view is still showing:** every navigation creates a new view object, and handlers check `isCurrent(view)` before moving on, so a save or delete that finishes after a capture can't close the capture's form. A capture during Edit is deferred until the edit closes; leaving Edit any other way (e.g. View existing) offers it in a toast instead of dropping it. Async views move initial focus in a layout effect, so focus lands in the same commit the view appears (and tests don't race it). Edit loads its row once rather than live, so a delete in another window can't wipe what's being typed. The status chip (`components/StatusChip.tsx`, `aria-expanded`, opens on click or ArrowDown) opens the panel's one shared status sheet (`components/StatusSheet.tsx`: `StatusSheetProvider` wraps `App`, so there's one dialog however long the list; a chip rendered outside it throws). It's a `Sheet` ("Change status", dismissible except on its date step) listing every status as a button, Active then Closed, the current one marked (`aria-current`) and focused; arrow keys move without changing anything, Enter or a tap picks. A status that implies an application while Date applied is empty switches the same sheet to a "When did you apply?" step (Set date / Skip / Choose another status, its reason linked to the date field); any other close changes nothing, and focus returns to the chip. Tests pick with `within(getByRole('dialog', { name: 'Change status' })).getByRole('button', { name })`, and render a chip on its own inside `StatusSheetProvider`. `rovingIndex` (`components/rovingIndex.ts`) is the arrow/Home/End rule shared with the tab bar and `Select` (which passes `wrap: false`, so its list stops at the ends). `expectNoHorizontalScroll` also checks open sheets. `App.handleStatusPick` calls `setStatus` and offers Undo in a toast. A toast is its own live region, so don't also `announce()` its message (screen readers would read it twice). Transient messages use the single `Toast` (its page region is `z-30`, above the rows' `z-10` chips and links and the floating button) (`components/Toast.tsx`, 5 s, paused on hover/focus), which M3 reuses for status Undo. A toast slides in, and after it goes it stays painted for `TOAST_EXIT_MS` while sliding out, `inert` and `aria-hidden` (tests advance past that before asserting it's gone). It sits above the floating button, which publishes `--fab-clearance`. Field validation and normalization live in `lib/applicationInput.ts`; `lib/applications.ts` re-validates on write. The form saves only through `saveApplication()` (`lib/applications.ts`), which validates once (with the status-aware Date applied rule), runs the duplicate check unless "Save anyway" (skipped when an edit leaves url, company and title unchanged), and returns either the saved row or the matches with their reason. Keep save rules there, not in components. It reads, validates and writes an edit in one transaction, and a status changed in the form follows the chip's rules. `addApplication` goes through it too. In an edit, leaving `resumeId` out keeps the link ('' clears it). It also links the resume (`resumeLink`): a new link must be a live, unarchived resume and stores its name as `resumeNameSnapshot`; an edit keeping the same resume keeps its snapshot. Display the resume's current name, falling back to the snapshot only when the resume is gone. A missing Date applied in input means "default to today"; an empty string means cleared.

**Detail view** (`components/ApplicationDetail.tsx`, spec §4.3): a page that slides in when opened from the list, not when coming back from Edit (`page page-slide-in`: the page clips its own sideways overflow and its children move inside it, so nothing scrolls sideways mid-slide). Its header has Back ("Back to applications"; Escape too, through a document listener that acts only when focus is in the page or on `body`, no `dialog[open]`, the page isn't inside `[inert]`, and nothing handled the key first; never on a held key's repeats), the company heading, Edit (the square-pen icon, named "Edit") and a ⋯ `MoreMenu` ("More actions for …") holding Delete; `MoreMenu` (`components/MoreMenu.tsx`) is the reusable ARIA menu button for rarer, riskier actions. The posting is a full-width button naming its site (`postingSite`: the host without "www.", international domains decoded from xn-- by `lib/punycode.ts`). The timeline (`components/StatusTimeline.tsx`) is a stepper with a dot per entry in its status color (`STATUS_SWATCH`, shared with the charts in `components/statusColors.ts`); dates are read-only until an entry's pencil opens a date field that saves only on its Save button or Enter (Escape cancels, focus returns to the pencil). Entries are keyed by index and time, so an editor whose entry changed elsewhere is dropped rather than saved onto another; after a save, the parent hands focus to the re-keyed entry's pencil. Never save a date on blur or change: a date picked from Chrome's calendar keeps focus in the field. In e2e, `expectNoHorizontalScroll` waits (capped) for animations to settle before measuring.

**Sheets** (`components/Sheet.tsx`): a bottom sheet is a native modal `<dialog>` (`showModal`; Chrome gives a modal dialog `overflow: auto`, which made it scroll, flashing a scrollbar, while the panel slid up from below), so the rest of the panel is inert while it's open. The `<dialog>` is `overflow: clip`, never `hidden`: a hidden-overflow dialog can still be scrolled by focus, so focusing the first field as it opened scrolled to the panel still below the edge and the sheet jumped instead of sliding (`e2e/motion.spec.ts`). It handles Escape on keydown itself (happy-dom fires no `cancel`), and ⌘/Ctrl+Enter (`isSubmitShortcut`, `components/submitShortcut.tsx`) clicks the button marked with `SUBMIT_SHORTCUT` (`data-sheet-submit`, `aria-keyshortcuts`) unless a control already took the key (`defaultPrevented`: an open `Select` or `Combobox` list picks with it), it's busy (`disabled`/`aria-disabled`), the key is held (`repeat`), focus is in its toast region, or the discard question is up, and stops it so a sheet opened inside another never presses the outer one's button; mark each sheet's main button, never a destructive one (the form's Save also draws `SubmitShortcutHint`), focuses its first control (or `initialFocus`), and on close slides out for `SHEET_ANIMATION_MS` (everything in it `inert` meanwhile, so a second click does nothing) before `close()`, then returns focus to the opener (unless something else took it) and calls `onClosed`. Do focus moves that target the page in `onClosed`, because the page is still inert while the sheet slides out. Unmounting it while open or sliding out does the same cleanup. `dismissible` lets a press-and-release outside close it (only for sheets without typing; a drag out of the panel doesn't count). `dirty` makes any close ask "Discard your changes?" first, in a small `alertdialog` centered over the sheet on a dimmed layer (inside the same `<dialog>`, so the toast layers and `focusOpenSheet` are unchanged), with Keep editing focused and the rest of the sheet inert; a click around it does nothing, Escape or Keep editing returns focus where it was, and any close (Discard, or from outside, like a capture) ends it at once rather than sliding out with it. The sheet's toast region sits above its dimmed layer (`z-20`), so a toast stays usable. Both dim layers use the `--scrim` token. From `showModal` until it has closed, a sheet registers its toast region (`components/toastLayer.ts`); the toast renders in the newest one, since a toast outside a modal dialog would be hidden, unclickable and unannounced. Each region is a polite live region that exists before a card arrives; a card that *moves* between regions (a sheet opened over it, or closed under it) arrives inside `aria-live="off"`, so it isn't announced twice, and its timer lives in `Toast`, so it doesn't restart. Every animation is skipped under `prefersReducedMotion()` (`components/motion.ts`); the keyframes are in `style.css`. Set the `inert` attribute with `inert(flag)` (`components/inert.ts`), since React 18 doesn't know the property. The floating button publishes its room with `usePublishedHeight` (`--fab-clearance`).

**Form layout (spec §4.2):** top fields, then a collapsed **More details** section that is `hidden`, not unmounted, so values and refs survive. It opens on its own for an error inside (then the field is focused), a captured value inside, or a stored value in Edit. The form is its own `Sheet` (`ApplicationForm` renders it; `open`/`onClosed` come from `App`): Back in the header (asking before discarding typed changes; a capture's prefill isn't typing), Save as the sheet's footer, joined to the `<form>` by `form=`, plus a hidden default submit button inside the form so Enter submits everywhere (user-event only looks inside the form). Field order: Company*, Job title, URL*, then Status and Date applied on one row (Status alone for Saved), then Resume; required fields get an asterisk beside (not inside) the label and `aria-required`; optional fields have just their label. The sheet opens on Company. Resume is a `Combobox` (`components/Combobox.tsx`, ARIA 1.2 combobox with a listbox: typing filters accent-insensitively, arrows move, Enter picks without submitting, Escape and leaving restore the choice, the empty choice shows as a placeholder) with a ghost + button that toggles the inline upload (its `PlusMinusIcon` turns into a −, and its name becomes "Close resume upload"; the upload's button says Upload, there's no Cancel, and Escape inside it closes just the upload, never the form, and does nothing mid-upload); a just-uploaded resume is offered at once, before the live list catches up. Currency is a `Combobox` too (`currencyLabel`: "EUR · Euro", common ones first). Status, Work mode, Per and Settings' first day of the week are a `Select` (`components/Select.tsx`: ARIA's select-only combobox, a `<button role="combobox">` named by its `<label htmlFor>`, keeping focus while `aria-activedescendant` points at the highlighted option; groups; Up/Down/Home/End/typeahead move without choosing, Enter or Space chooses, Escape and Tab close without choosing; `data-value` holds the value). Both lists open upward when the clipping area (a sheet's body) has no room below for the list's estimated height (`useDropDirection`, measured as they open); a list is as wide as its field, with long options wrapping. Number fields are `NumberField` (`lib/numberInput.ts`: `numberFieldText` drops anything a number in the locale can't contain as it's typed or pasted, `formatAmount` groups an amount once the field is left; parsing and errors stay in `parseSalary`), never `type="number"`; a dropped character keeps the caret in place. Numbers are always shown and parsed in Latin digits (`numberingSystem: 'latn'` in `formatNumber` and `numberSeparators`), since ar-EG's own digits would fail to parse. Edit shows stored salaries grouped (`formatNumber`), so leaving the field untouched doesn't count as a change. The weekly goal has −/+ buttons (and arrow keys) within 1–200 that save at once; at a limit they're `aria-disabled`, not `disabled`, since a button disabled under focus drops focus to the page. Source is `SourceField`: toggle chips (tap again to clear) and Other… with a text field. Notes is `AutoGrowTextarea` (3 lines, grows to about 12; `field-sizing: content`, measured on Chrome < 123). More details is an accordion section: a row button (named by its label, described by the hint of what's inside or what's filled in, which stays visible open or closed; no border under it) with the panel inside the same wrapper, growing and shrinking in height with no fade, the same 250 ms (`COLLAPSE_MS`) and easing both ways (`details-panel`: a one-row grid whose row animates between `0fr` and `1fr`, so the panel needs exactly one child holding the content and its layout classes, since the panel's own `display: grid` would override them; it clips only while animating, `overflow: clip` being part of the keyframes, so a menu or focus ring inside isn't cut off once open; hidden once `useCollapsing` says it has finished, inert meanwhile). Only a tap on the row animates it: opening on its own (an error inside, a capture, Edit) is instant (`data-instant`), since a field focused while the panel is still growing would be pushed out of view. Salary shows Minimum – Maximum on one row. In tests, set or read Source with `chooseSource`/`sourceValue` and pick a `Select` option with `chooseOption` (`tests/formHelpers.ts`; `chooseOption` in `e2e/fixtures.ts` too); don't poll a combobox's options inside `waitFor` (open it once and `findByRole('option')`). The remembered source, work mode and resume (`lib/formDefaults.ts`, `chrome.storage.local`) are written after every new application and read only by a manual Add; `App` waits for them before rendering the Add form, which reads defaults once, and when a resume is remembered also for that resume's row (one live `getResume`, whose result carries the id it was read for, since a live query keeps its last result while a new id loads), since `usableFormDefaults` drops it unless the picker offers it (`isResumeOffered` in `lib/resumes.ts`, the picker's own rule). After a capture its resume is remembered exactly (its form showed the remembered one), while only a source or work mode it had replaces the old one (its form never showed those, so their blanks don't mean "none"). In component tests, user-event can type into hidden fields under happy-dom, so assert visibility explicitly; Playwright catches it for real.

**List (spec §4.4):** `lib/listQuery.ts` filters, searches (accent- and case-insensitive, every word) and sorts, pure. A `ListQuery` is `{ search, sort, statuses, dates }`: `statuses` is any set of statuses (none means all; `toggleStatus`/`toggleGroup`/`groupState` handle the chips, Active and Closed being groups), and `dates` is a Date applied preset or Custom resolved with the Stats ranges (`dateFilterRange`, given a `QueryContext` of today and the week start; an unfinished Custom range filters nothing and isn't counted; a date filter hides jobs without a usable Date applied, by the same `inRange` rule as Stats; the Custom dates are kept while a preset is picked, and Custom first opens on the last 30 days via `customStart`, shared with Stats). `activeFilterCount(query, context)` counts a date filter that really filters and a status filter, never the sort. The query lives in `App` so it survives navigation. The search filters once typing pauses (`useDebouncedSearch`, `SEARCH_DEBOUNCE_MS`; a blank search applies at once): the box shows `query.search` as typed, and `ApplicationList` filters and freezes on the settled value, so a Clear before it settles leaves nothing behind (the Resumes search debounces the same way; in tests, `waitFor` the result). `ListControls` is the search box plus a Filters button (with the count) that opens the filter sheet (sort, date, status chips) as a draft: only **Apply** changes the query (keeping the search, which the sheet doesn't hold), closing any other way discards it, each opening starts from the applied query, and Reset clears the draft's filters and sort without applying; in tests use `filterBy`/`apply` (`components/ListControls.test.tsx`). Apply refuses a Custom range with a missing or impossible date (the sheet stays open, focus on that date) and skips a draft with the same effect (`sameFiltersAndSort`: Custom dates left over behind a preset don't count), so a frozen list never refreshes for nothing. A capture closes the sheet (`ListControls`' `active`, from `App`'s `!sheetView`). The sort, like Settings' Theme, is a `SegmentedControl` (`components/SegmentedControl.tsx`: native radios, a `data-marker` that slides under the chosen segment, sized from the same `--seg-pad`/`--seg-gap` variables as its grid). `ApplicationList` freezes row order and membership per query (and per day, only while a date filter is on) while it's mounted (`frozen`: ranks plus the ids shown, refreshed when the query changes or on remount), so a status change can't move or hide a row from under the pointer. `listApplications` alone filters soft-deleted rows; `queryApplications` takes its output. A row is a card: the company (truncated, full name in `title`) with its status chip, then location and work mode, title, and "Applied …" (or "Added …"), with the posting link on the right; the company button's `::after` (class `row-open`) covers the card, so the whole card opens the job, while the chip and link sit above it (`relative z-10`). The resume isn't on the row.

**Showing dates:** stored dates stay `YYYY-MM-DD` (local) or ISO timestamps; display them with `formatLocalDate` / `formatTimestampDate` (`lib/dates.ts`), never raw and never via `new Date('YYYY-MM-DD')`, which parses as UTC and can show the previous day.

**UI constraint:** every screen lives in a ~320–400px side panel. Design for that width; changing status is a one-tap chip with Undo, not a Kanban board.

## Definition of done

A task or milestone is done only when all of these are true. Report anything not met instead of calling it done.

1. **The slice runs end to end.** The milestone's "Slice" scenario (in `milestones.md`) works in a production build (`npm run build`, loaded unpacked), not just in dev mode, and a Playwright test covers it.
2. **Checks are green:** `npm run lint`, `npx tsc --noEmit`, `npx vitest run`, and `npx playwright test`.
3. **Tests exist for new logic.** Anything new in `lib/` has unit tests, including the cases the milestone lists. Bug fixes come with a regression test.
4. **No permission or network creep.** The manifest permissions match spec §8 for this point in the build. There are no new host permissions, `fetch` calls, or remote code.
5. **Schema changes migrate.** Dexie schema changes add a new version with an upgrade path, and a test opens a database from the previous version.
6. **The UI fits the panel.** New screens work at 320px width with no horizontal scroll and are fully keyboard-operable. From M6 on, they also work in both light and dark themes.
7. **Docs match reality.** `spec.md` reflects any changed behavior, including verified or disproven Chrome API assumptions. `CLAUDE.md` commands and architecture match the code. The milestone is checked off in `milestones.md`.

## Branching & PR workflow

This is a solo repo on GitHub with trunk-based development. Claude runs the whole loop with `gh` (branch, commit, PR, self-review, merge) and hands a PR back to the owner only in the cases listed under step 6.

- **`main` is always releasable.** Never commit directly to it. A GitHub ruleset requires a PR and green CI, and allows squash merge only.
- **Branches are short-lived, one per task within a milestone:** `m<N>/<kebab-task>`, e.g. `m1/context-menu-capture` or `m2/normalize-url`. Keep each branch to roughly a day of work. A milestone usually takes several PRs.
- **Commits** are small and use conventional prefixes (`feat:`, `fix:`, `test:`, `refactor:`, `chore:`, `docs:`). The squash-merge title is the PR title in the same format, e.g. `feat(m1): open side panel from context menu`.

**Loop for each task:**
1. `git switch main && git pull`, then `git switch -c m<N>/<task>`.
2. Build it, then meet the Definition of done items that apply to the task.
3. Push, then `gh pr create`. The PR body covers what changed, which milestone it belongs to, how it was verified (commands and results), and any DoD items deferred to a later PR in the same milestone.
4. **Self-review before merging.** Run `/code-review` on the PR and fix the findings. Also check the manifest diff and any Dexie schema change.
5. Wait for CI (`gh pr checks --watch`), then `gh pr merge --squash --delete-branch`.
6. **Hand back to the owner** (leave the PR open and explain why) when any of these apply:
   - A permission, host access, or network call changes.
   - A product decision in `spec.md` changes, rather than a clarification or a verified assumption.
   - A Dexie migration could lose or reshape existing user data.
   - CI can't be made green.
   - Self-review leaves an unresolved concern.

**Milestones and releases:**
- When the last PR of a milestone merges and the full DoD holds, tag `main` as `v0.<N>.0` (e.g. `v0.1.0` after M1) with `gh release create`, and attach the `npm run zip` output.
- Store releases begin at `v1.0.0` after M9.
- Hotfixes use a `fix/<desc>` branch and bump the patch version.

## Out of scope for v1 (don't build unless spec.md changes)

Follow-up reminders or notifications, auto-detecting submitted applications, site-specific scrapers, accounts or sync, custom statuses, Kanban, and a show/hide-rejections setting.
